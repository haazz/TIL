# 인증 (Authentication)과 인가 (Authorization)

- **인증** : 사용자가 누구인지, 유효한 사용자가 맞는지 확인하는 것이다. (로그인)
- **인가** : 인증된 사용자가 특정 자원/기능에 접근할 **권한**이 있는지 확인하는 것이다.
- 순서: 먼저 인증(누구인지) → 그다음 인가(무엇을 할 수 있는지).

# 세션 기반 인증

- 서버가 로그인 상태(세션)를 서버 메모리나 DB에 저장하고, 클라이언트엔 세션 ID만 쿠키로 준다.
- 장점: 서버가 상태를 갖고 있어 강제 로그아웃(세션 무효화)이 쉽다.
- 단점: 서버를 확장(scale-out)하면 세션을 공유할 저장소(Redis 등)가 필요하다.

# JWT (JSON Web Token) 기반 인증

- 토큰 안에 사용자 정보를 담고 **서명**하여 클라이언트가 들고 다닌다. 서버는 상태를 저장하지 않는다(stateless).
- 구조: Header.Payload.Signature
- 장점: 서버가 무상태라 확장에 유리하다.
- 단점:
  - **즉시 무효화가 어렵다.** 무상태라 로그아웃/탈취 시 만료 전까지 강제로 막기 힘들다. (블랙리스트를 Redis에 두어 보완)
  - 페이로드는 **암호화가 아니라 서명**일 뿐이다. Base64 디코딩으로 내용이 보이므로 민감정보를 넣으면 안 된다.
  - 토큰 크기가 세션 ID보다 크다.

# Access Token과 Refresh Token

- **Access Token** : 실제 인증에 쓰는 토큰. 탈취 위험 때문에 만료를 짧게(분 단위) 둔다.
- **Refresh Token** : Access Token이 만료되면 재발급받기 위한 토큰. 만료를 길게 둔다.
- Access가 만료되면 Refresh로 새 Access를 발급받아, 짧은 만료의 보안성과 잦은 재로그인의 불편함을 절충한다.
