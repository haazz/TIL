# 동시성 제어와 락

- 여러 트랜잭션이 같은 데이터를 동시에 수정할 때 발생하는 정합성 문제(갱신 손실 등)를 막기 위한 기법이다.
- 크게 낙관적 락과 비관적 락으로 나뉜다.

# 낙관적 락 (Optimistic Lock)

- "충돌이 드물 것"이라고 낙관하고, 실제 DB 락을 걸지 않는다.
- 보통 **version 컬럼**을 두고, 수정 시점에 버전이 그대로인지 확인한다.
- 버전이 바뀌었으면(다른 트랜잭션이 먼저 수정) 충돌로 보고 실패 처리하거나 재시도한다.
- 장점: 락 비용이 없어 성능이 좋다.
- 단점: 충돌이 잦으면 재시도가 많아져 비효율적이다.
- 적합: **충돌 빈도가 낮은** 경우.

# 비관적 락 (Pessimistic Lock)

- "충돌이 자주 날 것"이라고 비관하고, 데이터를 읽는 시점에 **DB 락을 건다.**
- `SELECT ... FOR UPDATE`로 행을 잠가, 다른 트랜잭션이 끝날 때까지 기다리게 한다.
- 장점: 충돌을 확실히 막아 정합성을 보장한다.
- 단점: 락 대기로 처리량이 떨어지고, 데드락 위험이 있다.
- 적합: **충돌 빈도가 높고** 정합성이 critical한 경우.

# 선택 기준

- 충돌이 드물다 → 낙관적 락
- 충돌이 잦고 정합성이 중요하다 → 비관적 락
- 예: 쿠폰/재고 차감처럼 동시 요청이 몰리고 수량 정합성이 중요한 경우 비관적 락이 적합하다.
- 추가 인프라(Redis 등)를 쓰는 분산 락도 대안이지만 운영 복잡도가 올라간다.
